DATENSICHERHEIT – SPEICHERMANAGEMENT (seit v2.10.71)
============================================================
Die Datenbank ist durch DREI Schutzschichten vor Überschreiben geschützt.
Bei Änderungen am Speicher-/Sync-Code diese NIEMALS umgehen:

SCHICHT 1 – Client-Sperre:
  - saveData() sendet IMMER appDataRev (baseRev) im Payload.
  - forceSaveData() / forceSaveDataMobile() sind BLOCKIERT wenn
    appDataRev === null (= Offline-/Cache-Daten ohne gültige Revision).
  - „Meine Version erzwingen" im Konflikt-Dialog ist nur mit gültiger
    Revision möglich.
  → Bei Änderungen: appDataRev darf NIEMALS künstlich gesetzt werden.

SCHICHT 2 – Server Optimistic Locking (DataService::saveAllData):
  - baseRev === null UND curRev > 0 → 409 Conflict (v2.10.71)
  - baseRev !== curRev → 409 Conflict (seit v2.10.50)
  - Nur bei leerer DB (Ersteinrichtung) oder explizitem force + gültiger
    Rev wird ohne Prüfung geschrieben.
  → Bei Änderungen: NIEMALS den Locking-Check entfernen oder lockern.

SCHICHT 3 – Server Force-Guard (letzte Verteidigung):
  - Selbst bei force=true + baseRev=null: wenn der Payload weniger als
    die Hälfte der bestehenden Baustellen enthält → ABGELEHNT.
  → Fängt Bugs in Schicht 1+2 ab. Nicht entfernen.

OFFLINE-VERHALTEN:
  - loadFromLocalStorage() setzt appDataBaseline (für Auto-Merge) aber
    appDataRev = null (signalisiert: nicht server-synchron).
  - _scheduleOnlineRefresh() startet automatisch: sobald Netz verfügbar →
    loadData() → frische Server-Daten laden → Re-Render.
  - syncOfflineData() sendet baseRev mit; bei Konflikt → Auto-Merge
    (nicht blindes Überschreiben).
  → NIEMALS appDataRev bei Offline-Daten künstlich auf einen Wert setzen.

AUTO-MERGE (resolveSaveConflict):
  - Vergleicht Server-Stand gegen appDataBaseline (letzter bekannter Sync).
  - Disjunkte Änderungen (verschiedene Baustellen) → lautlos zusammengeführt.
  - Echte Überschneidung → Dialog (Nutzer entscheidet).
  - Nach „Später entscheiden" → zyklischer Hintergrund-Retry (30s, max 5 Min).
  → appDataBaseline MUSS bei jedem erfolgreichen Load/Save aktualisiert werden.

PROJEKT-PRESENCE (seit v2.10.72):
  - Client sendet alle 60s Heartbeat (project_heartbeat, _idle=1).
  - Andere Nutzer sehen „🔒 XY bearbeitet gerade" im Projekt-Header.
  - Kein harter Lock – nur Info zur Konfliktvermeidung.
  - Heartbeats verfallen nach 120s ohne Aktualisierung.

ZUSAMMENFASSUNG DER GESCHÜTZTEN SAVE-PFADE:
  Desktop saveData()           → baseRev-Pflicht
  Desktop forceSaveData()      → Client-Sperre + Server-Guard
  Desktop syncOfflineData()    → baseRev + Auto-Merge
  Desktop _applyMergedAndSave()→ frische serverRev (kein Force)
  Mobile forceSaveDataMobile() → Client-Sperre + Server-Guard
  Mobile normaler Save         → baseRev-Pflicht
  Server saveAllData(null,false) → lehnt ab (curRev>0)
  Server saveAllData(null,true)  → Force-Guard (Ratio-Check)

DEPLOYMENT-WARNUNG – DATENVERLUST-RISIKO (Vorfall 2026-06-05)
============================================================
PROBLEM (analysiert): `sudo docker compose up -d --build` stoppt den alten
  Container abrupt. SQLite läuft im WAL-Modus (Write-Ahead Log) und schreibt
  Änderungen zunächst in database.sqlite-wal statt direkt in database.sqlite.
  Beim abrupten Container-Stop kann der WAL-Checkpoint nicht mehr sauber
  abgeschlossen werden. Nach dem Neustart fehlen die WAL-Sidecar-Dateien
  (-wal, -shm) oder sind inkonsistent → SQLite fällt auf den letzten
  vollständigen Checkpoint zurück → Datenverlust der nicht-checkpointed Änderungen.
  Das automatische Tagesbackup (07:21 Uhr) lief danach und sicherte
  die bereits leere DB. Letztes brauchbares Backup: Jun 3, 09:12 (6,5 MB).
  Verloren: Änderungen vom 3.–5. Juni.

  HINWEIS: `docker compose down -v` wäre noch schlimmer (löscht Volumes
  komplett). Auch ohne -v kann es durch WAL-Inkonsistenz zu Datenverlust kommen.

VERPFLICHTENDE SCHRITTE VOR JEDEM DEPLOYMENT:
  1. Manuelles Backup + WAL-Checkpoint erzwingen:
       docker exec baukalkulation-es-app php -r "
         \$db=new PDO('sqlite:/var/www/html/data/database.sqlite');
         \$db->exec('PRAGMA wal_checkpoint(FULL)');
         copy('/var/www/html/data/database.sqlite',
              '/var/www/html/data/backups/pre_deploy_'.date('Ymd_His').'.sqlite');
         echo 'Backup + Checkpoint OK';"
  2. Datenmengen notieren (Soll-Zustand für Post-Deploy-Vergleich):
       docker exec baukalkulation-es-app php -r "
         \$db=new PDO('sqlite:/var/www/html/data/database.sqlite');
         echo 'Baustellen: '.\$db->query('SELECT COUNT(*) FROM baustellen')->fetchColumn().PHP_EOL;
         echo 'Kunden: '.\$db->query('SELECT COUNT(*) FROM kunden')->fetchColumn().PHP_EOL;
         echo 'User: '.\$db->query('SELECT COUNT(*) FROM users')->fetchColumn().PHP_EOL;"
  3. Deploy ausführen:
       cp -r deploy./* .
       docker compose up -d --build
  4. Post-Deploy-Check – Zahlen müssen identisch sein wie in Schritt 2:
       docker exec baukalkulation-es-app php -r "
         \$db=new PDO('sqlite:/var/www/html/data/database.sqlite');
         echo 'Baustellen: '.\$db->query('SELECT COUNT(*) FROM baustellen')->fetchColumn().PHP_EOL;
         echo 'Kunden: '.\$db->query('SELECT COUNT(*) FROM kunden')->fetchColumn().PHP_EOL;
         echo 'User: '.\$db->query('SELECT COUNT(*) FROM users')->fetchColumn().PHP_EOL;"
     Wenn Baustellen/Kunden = 0 → SOFORT Backup aus Schritt 1 wiederherstellen!

WIEDERHERSTELLUNG falls Daten weg:
  # Neuestes gültiges Backup ermitteln (nach Größe: >1 MB = echte Daten):
  ls -lah /home/stadlermini/elektrotechnik-stadler/Baukalkulation/data/backups/
  # Restore:
  docker exec baukalkulation-es-app php -r "
    \$src='/var/www/html/data/backups/<DATUM>/database.sqlite';
    \$dst='/var/www/html/data/database.sqlite';
    copy(\$dst,\$dst.'.leer'); copy(\$src,\$dst); echo 'Wiederhergestellt';"
  # Migrationen auf wiederhergestellter DB ausführen:
  cd /home/stadlermini/elektrotechnik-stadler/Baukalkulation && docker compose restart

GELÖSTE FEHLER – PRÄVENTION (damit sie nicht erneut passieren)
============================================================

1) CSP BLOCKIERT EXTERNE CDNs (cdnjs.cloudflare.com)  [Vorfall 2026-06]
   SYMPTOME: PDF-Report (mobil) schlägt fehl, Auswertungs-Diagramme bleiben
     leer, Excel-Export tut nichts – aber KEINE offensichtliche Fehlermeldung.
   URSACHE: .htaccess setzt `Content-Security-Policy: script-src 'self'
     'unsafe-inline' 'unsafe-eval'` → ALLE Skripte von externen CDNs werden
     blockiert. Chart.js / xlsx / html2pdf wurden nie geladen
     → `typeof Chart/XLSX/html2pdf === 'undefined'` → Funktionen brechen
     still ab (z.B. `if (typeof Chart === 'undefined') return;`).
   REGEL: NIEMALS Dritt-Bibliotheken per `<script src="https://cdnjs...">`
     oder dynamischem CDN-Loader einbinden. IMMER lokal in `lib/` hosten und
     per relativer URL `lib/<datei>.min.js` laden ('self' ist CSP-erlaubt).
     Aktuell lokal: lib/chart.umd.min.js, lib/xlsx.full.min.js,
     lib/html2pdf.bundle.min.js.
   WICHTIG: Statische Web-Bibliotheken gehören nach `lib/` – NICHT nach
     `vendor/` (das ist via .dockerignore für Composer ausgeschlossen und
     landet NICHT im Image!).
   WICHTIG: Neue lib/-Dateien IMMER auch in sw.js PRECACHE_URLS aufnehmen.
     Achtung: cache.addAll() schlägt KOMPLETT fehl, wenn nur eine URL nicht
     erreichbar ist (war der Grund, warum Offline-Support mit CDN-URL brach).

2) HTML2CANVAS / HTML2PDF ERZEUGT WEISSE / LEERE SEITE
   SYMPTOME: PDF wird gespeichert, aber das Dokument ist eine leere weiße Seite.
   URSACHE: Render-Container stand auf `position:fixed; left:-9999px;
     top:-9999px` (doppelt aus dem Viewport) → html2canvas erfasst in manchen
     Browsern eine leere Fläche.
   REGEL: Off-Screen-Container für html2pdf/html2canvas mit `left:-9999px;
     top:0` positionieren (nur horizontal aus dem Bild, top:0). So in der
     funktionierenden Mobil-Variante und in _saveRechnungPdfBackground.
   MERKHILFE: Wird trotzdem eine Datei (aber leer) gespeichert, lief html2pdf
     – dann ist es ein RENDER-Problem (top:0), kein Lade-Problem (CSP/lib).

3) NEUE EINSTELLUNG WIRD NICHT GESPEICHERT (still verworfen)
   SYMPTOME: save_settings meldet ok, aber der Wert ist nach Reload weg.
   URSACHE: AdminActions::saveSettingsAction() übernimmt NUR Schlüssel, die
     bereits in Auth::loadSettings()-DEFAULTS existieren (`$allowed`).
     Unbekannte Keys werden ignoriert.
   REGEL: Jede neue Einstellung ZUERST mit Default-Wert in Auth.php (Array in
     loadSettings) eintragen, sonst greift der Allowlist-Filter. Typ beachten:
     bool/array/string werden je nach Default-Typ gecastet (Zahl als string!).
   Beispiele dieser Art: zeiterfassung_abschluss_jahr,
     auswertung_archiv_abschluss_jahr.

4) MOBILE MODUL-CACHE-VERSIONEN WEICHEN VON DESKTOP AB
   SYMPTOME: Modul verhält sich mobil anders / veraltet (z.B. lager, aufmass).
   URSACHE: ?v=NN in mobile.html (Modul-Loader) hinkte hinter script.js
     (loadOptionalModule) zurück.
   REGEL: Nach JEDER Änderung an modules/<name>/*.js|*.css die ?v=NN an BEIDEN
     Stellen synchron anheben (script.js UND mobile.html), css UND js getrennt.

5) DATENINTEGRITÄT BEI „AUSBLENDEN"-FEATURES
   REGEL: Funktionen wie Jahreswechsel-Abschluss blenden Daten NUR per
